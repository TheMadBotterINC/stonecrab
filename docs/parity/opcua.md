# OPC UA parity record
Baseline: `upstream/manifest.toml`, Apache PLC4X v1.0.0 (tag `v1.0.0`),
commit `ea229918f5d07700e04d7d69ab1645da679cb700`.

State at slice S43: nothing is implemented. Stonecrab has no OPC UA code, no OPC UA test
and no OPC UA connection string yet, so every row below is `planned (M3)` or `deferred`.
OPC UA is milestone M3 of `docs/POST_ALPHA_PLAN.md` section 4: the secure channel and
session with the upstream security policies, chunking, read, a browse API with its own
types, native subscriptions, staged write, and the discovery handshake, with trust-failure,
credential and session-renewal cases and interop against an independent server such as
open62541. Decision E3 puts the MSpec generator (Phase G, S65 to S67) before M3, so the
wire codec rows are planned against a generated codec proven on Modbus first. The TLS and
TLS-PSK transports that M3 also lists are for Modbus: upstream OPC UA uses no TLS transport
(`OPCUA-TRANSPORT-TLS`). The PLC4X OPC UA Server tool (manifest `inventory.tool_opcua_server`,
repository `apache/plc4x-extras`, outside the pinned baseline) is a tool, not part of this
driver, and is tracked by the tools record, not here.

Slice S75 (2026-10-29) assigned every planned row to a slice of M3 (S76 to S123); see "Slice assignment (S75)" below. Nothing was implemented and no status changed.

Sources: the Java driver `plc4j/drivers/opcua` is the baseline (manifest `inventory.opcua`,
read in S41). The Go driver `plc4go/internal/opcua` (manifest `inventory.go_opcua`, read in
S42) is a partial second implementation; its rows are in the section "Go implementation" and
are never obligations. No source was run: every upstream statement here is read from the
pinned source, and where the manifest marks it UNCERTAIN the row says so. The manifest has no
`[[backlog]]` row for OPC UA (no capability found in Go that Java lacks), see "Backlog from
other languages".

Status vocabulary, as used in the Status column:

- `planned (Mn)`: Stonecrab will port the behavior in milestone `Mn`. The Test ids column
  names at least one planned test, prefixed with `planned:`. A planned test id is a name
  chosen now so every required behavior maps to a test; it does not exist in the repository
  and no row may be called implemented until a test of that name passes.
- `deferred (<reason>)`: Stonecrab will not port the behavior now. The reason is one of: a
  placeholder or throw upstream (`upstream placeholder`), a capability the Java baseline
  does not have (`not in Java`), a Go-only behavior (`Go only`), a decision (`E5`, `E6`), or
  a short phrase. Test ids is `none` unless a rejection is planned.
- `implemented`, `automated-verified` and `hardware-verified` are not used yet. When a row
  lands it follows the rules in `docs/parity/modbus.md`, and `scripts/parity-check.sh`
  enforces them: none of the rows here is subject to its code-reference checks.

Row count: 228 rows with ids (every table), 195 `planned (M3)` and 33 `deferred`; none is
implemented. The Divergences, quirk and Go tables reuse no ids.

How row ids are used: the first column of every table is a stable id with the prefix
`OPCUA-`. Ids are never renumbered; a retired row keeps its id and says so.

## Required evidence before an OPC UA claim
No OPC UA row is `implemented`. Before any is, the plan requires interop against an
independent server (open62541 is the plan's example), named-device evidence before any
hardware claim, and the Milo-based upstream tests are not behavior evidence. The first
rows to reach `automated-verified` are expected to be `OPCUA-OP-CONNECT` with
`OPCUA-POLICY-NONE` (Hello to ActivateSession against the server) and `OPCUA-OP-READ`.
Chunking, renewal and trust-failure rows need fault hooks the independent server may not
offer; those stay `implemented` over the fake transport (D21).
